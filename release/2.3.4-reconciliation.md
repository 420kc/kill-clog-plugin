## Findings

### A. Every-open capture still restarts the panel lookup

`KillClogPanel.onBulkCaptureComplete` in 2.3.4 (line 1763) unconditionally changes
the search text to the local player, cancels the active lookup, and calls
`doLookup`. Since full capture now runs on every log open, opening one's own
log while viewing another player can replace that view. It also restarts lookup
work even for unchanged captures.

Both future branches contain the fixes from `211631c6` and `e403c7d8`: quietly
refresh an already displayed self log, preserve other-player views, fence stale
in-flight results, and redraw comparison colors/totals in the correct order.
The first fix depends on local-source provenance through `ClogService`,
`ClogResult`, and `LookupSession`; backport the dependency chain deliberately,
not just the panel method. This corrects the behavior whose frequency the
maintenance candidate expanded.

### B. Known live-counter double count remains

2.3.4 retains the manual increment in `LocalClogCache.mergeObtainedItem`
(lines 1512, 1557-1562). If the game counter arrives first, recording the unlock
increments the already-current total again. Both future branches contain
`31d4f597`, which leaves scalar totals to game counters and records item history
separately.

Reproduction: exported the exact candidate into
`C:/Users/dylan/AppData/Local/Temp/killclog-234-reconcile-2d9pqj76`, inserted the
existing `liveUnlockTotalsFollowGameCountersInEitherEventOrder` test from
`31d4f597` into its original test class, and ran that one test. It failed with
`expected:<1> but was:<2>`. Applying only that commit's two production-file
patches in the temporary copy made the same test pass (BUILD SUCCESSFUL).
Logs: `reconcile-gate.log` and `reconcile-counter-fixed.log` in that directory.
This is an inherited bug left in the candidate, not a new regression versus
shipped 2.3.3. It is nevertheless a directly relevant missed sync correction.

### C. Canonical reverse-index dedupe was omitted

Fable's finding 1 is already guarded in both future branches: add a category to
an item's reverse index only when it is not already present. The adapted
2.3.4 parser at `ClogIndex.java:102` omitted that guard. Restore the guard and
exercise production parsing, because the existing test seam does not cover
multiple raw catalog forms mapping to the same canonical slot.

### D. Cache-ownership hardening remains outside this candidate

Both future branches contain `064c09b0`: unreadable/missing ledger and resident
owner checks around adoption, rename, and writes. The maintenance branch still
has 2.3.3 behavior there while changing capture replacement and retry writes.
This is an inherited safety gap, not proven introduced by this backport. Treat
it as an explicit reconciliation decision; recommending submission without
calling out this later correction in the same persistence subsystem was too broad.
Recommend including this existing safety slice with its failure-path tests and
independent review before shipping the combined refresh update.

## Confirmed matches and intentional differences

`ManualClogSync`, `ClogItemCanonicalizer`, `TitleTooltip`, `SkillTooltip`,
`SkillClogSectionRenderer`, `PvmSummaryTooltip`, `SkillsTooltip`, and
`SummaryTooltip`. The obsolete overlay and visible-category reader classes
are absent in all three.

`TooltipItemHover` matches the refactor branch. Frozen 2.4.0 additionally has
its later Chompy display-label call, which the refactor branch has not yet
integrated. That pre-existing future-branch divergence is not caused by 2.3.4.

Other differences include local-source attribution, acquisition-date history,
pending ambiguous unlocks, newer totals/presentation behavior, appearance,
taxonomy, and the structural refactor. They must remain on their future lines;
the audit does not authorize replacing those lines with the maintenance tree.
Fable's variant-discovery and alternate-ID metadata limitations also exist in
the future implementation and are not losses unique to this backport.
